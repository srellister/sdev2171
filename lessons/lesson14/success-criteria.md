# Lesson 14 Success Criteria

Use this checklist before you decide that lesson 14 is complete.

## Stable Request-State Workflow
To count as `resolved`, your project should have:

- one working request screen connected to the local backend
- one visible loading state
- one visible success state with rendered list data
- one visible error state
- one working retry path after failure
- intentional testing evidence for loading, success, and error

## Explanation Standard
You should also be able to explain:

- what starts the request
- which state value controls loading
- which state value stores the error
- what visible evidence proves success
- what visible evidence proves failure

## Acceptable Incomplete Progress
If the workflow is not fully stable yet, you may still record `partial` only when:

- the current blocker is named clearly
- the exact file or logic area is identified
- one next action is written down

## Not Yet Acceptable
You are still `blocked` if:

- the backend path is not confirmed
- the request target is unclear
- you cannot trigger or observe the loading branch
- you cannot explain why the error branch is not appearing
- you have no named next action
